# Design an auditable RSC data-exposure boundary

Collection: catalog · ID: `next-lab-rsc-data-boundary` · Mode: **guided**

## Business context

Developers assume that anything computed in a Server Component cannot reach a browser.

## Task

Design the system for A regulated portal with internal account records and public client islands. Produce the component/data-flow diagram, request and mutation contracts, cache/trust boundaries, capacity assumptions, failure recovery and rollout gates. State which decisions change between Next.js 15 and 16 instead of using a framework API as a substitute for an architectural guarantee.

## Candidate tasks

- Draw components and annotate ownership of data, identity, caches and durable work.
- Specify contracts/schema and quantify the capacity/freshness assumptions.
- Walk through the failure scenario and design measurable acceptance tests.
- Compare the reference decisions and answer the changed-requirement interview prompt.

## Constraints

- Prevent sensitive props and errors from crossing the boundary.
- Centralize authorized data access.
- Provide reviewable DTO contracts and regression evidence.

## Follow-up questions

- Would encryption of transport eliminate the risk?

## Next.js version and verification scope

Mode: **architecture**.

Next.js 15: Use patched Next.js 15 and the router family named by the file path. Await request APIs where the App Router contract requires it; validate behavior in a production build.

Next.js 16: Applies to Next.js 16.4.5. Cache Components is disabled unless the exercise explicitly enables it. The simulator itself remains on 16.4.3.

### Acceptance evidence

- Insert sentinel secrets and inspect HTML, RSC, script chunks and action responses.
- Test different actors against the same resource ID.
- Fail a server read and verify production error redaction.
