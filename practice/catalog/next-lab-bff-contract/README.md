# Design a Next.js backend-for-frontend with bounded ownership

Collection: catalog · ID: `next-lab-bff-contract` · Mode: **guided**

## Business context

One Route Handler proxies arbitrary user URLs with server credentials and buffers unlimited responses.

## Task

Design the system for Web UI plus mobile/external consumers; three upstream services. Produce the component/data-flow diagram, request and mutation contracts, cache/trust boundaries, capacity assumptions, failure recovery and rollout gates. State which decisions change between Next.js 15 and 16 instead of using a framework API as a substitute for an architectural guarantee.

## Candidate tasks

- Draw components and annotate ownership of data, identity, caches and durable work.
- Specify contracts/schema and quantify the capacity/freshness assumptions.
- Walk through the failure scenario and design measurable acceptance tests.
- Compare the reference decisions and answer the changed-requirement interview prompt.

## Constraints

- Expose an explicit admitted API surface.
- Keep credentials server-side.
- Bound work and separate public consumer contracts from UI composition.

## Follow-up questions

- Should mobile clients depend on React Flight payloads?

## Next.js version and verification scope

Mode: **architecture**.

Next.js 15: Use patched Next.js 15 and the router family named by the file path. Await request APIs where the App Router contract requires it; validate behavior in a production build.

Next.js 16: Applies to Next.js 16.4.5. Cache Components is disabled unless the exercise explicitly enables it. The simulator itself remains on 16.4.3.

### Acceptance evidence

- Test malformed, oversized and unauthorized requests.
- Inject stalls, partial bodies and non-JSON upstream failures.
- Prove no credential crosses an unauthorized host or appears in client errors.
