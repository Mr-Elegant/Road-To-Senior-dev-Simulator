Connected Production Database Architecture (Neon PostgreSQL + Prisma)

The application features a fully configured, live Neon Serverless PostgreSQL database synchronized via Prisma ORM. Persistence follows a decoupled StorageAdapter pattern: candidate actions (attempts, bookmarks, code submissions, custom notes, Tier 1 progress, and SQL track progress) are instantly committed to browser local storage for zero-latency UX, while simultaneously dispatching non-blocking background synchronization requests to the PostgreSQL backend route handlers.

PostgreSQL Schema Specification (prisma/schema.prisma):
The database tracks user entities with unified JSON progress trees: model User { id String @id @default(uuid()), email String? @unique, attempts Json @default("[]"), bookmarkedIds Json @default("[]"), notes Json @default("{}"), tier1Progress Json?, sqlProgress Json?, streak Int @default(0), lastActive DateTime @default(now()), createdAt DateTime @default(now()), updatedAt DateTime @updatedAt }.

Security Rationale: Why Arbitrary Code Never Executes on the Server

Security Boundary Isolation: In many naive interview platforms, user-submitted code is sent to the backend and executed inside containers. This introduces container breakout vulnerabilities, crypto-mining attacks, and severe resource exhaustion. In Full Stack Interview Lab, all user code executes strictly inside client-side isolated sandboxes (Web Workers and isolated IFrames) and in-browser SQL relational engines (AlaSQL). The server route handlers remain stateless, fast, and protected from arbitrary code execution.

2. Deep Dive: Conversational AI Interviewer AI Architecture

The AI Interviewer is powered by the official @google/genai JavaScript SDK and connected to Google's gemini-3.5-flash (with fallback to gemini-2.0-flash). It simulates an adaptive, multi-turn interview with a Principal Engineer or Hiring Committee Bar Raiser.

Key Engineering Pillars of the AI Interview Engine

1. Strict Server-Side Isolation of Credentials

The Gemini API key is read exclusively from process.env.GEMINI_API_KEY on the server side in src/app/api/ai-interview/route.ts and src/app/api/sql/evaluate/route.ts. The key is never serialized, never sent to client-side components, and never returned in network responses.

2. Multi-Turn Session State Machine

The interview state is tracked through a structured session state machine:

  • config: Role (e.g. Senior Full-Stack Engineer L5, Database Architect L6), Technology Domain, Seniority Bar, and Turn Limit.
  • currentQuestion: The dynamic scenario statement generated by Gemini.
  • history: The chronologically preserved conversation turns (Candidate answers and AI questions).
  • turnFeedback: Per-turn technical critique evaluating trade-offs, potential edge cases, and architectural reasoning.
  • finalAssessment: Generated upon interview conclusion across 4 key dimensions: System Architecture, Correctness & Edge Cases, Production Readiness, and Trade-off Analysis.

3. High-Fidelity Deterministic Offline Fallback

Zero-Downtime Guarantee: If GEMINI_API_KEY is not provided, if the API rate limit is reached, or if the client is working in an offline environment, the system gracefully shifts to the deterministic offline simulator in src/lib/gemini/offlineFallback.ts and src/lib/gemini/sqlPrompts.ts. Candidates can continue practicing without UI crashes or frozen screens.

4. Rate Limiting & Timeout Protections

The service implements an in-memory sliding-window rate limiter restricting traffic to 30 requests per minute per server process. Every outbound call to Google Gemini is wrapped with a strict 35-second timeout guard using AbortSignal.timeout(35000) to prevent hanging connections.

The 4 Progression Tiers

  • Tier 1: Beginner SQL (30 Qs): Relational fundamentals, SELECT, WHERE, ORDER BY, LIMIT, INNER/LEFT/RIGHT JOINs, GROUP BY & HAVING, NULL semantics (IS NULL, COALESCE), and Primary/Foreign Key constraints.
  • Tier 2: Intermediate SQL (30 Qs): Analytical window functions (DENSE_RANK, SUM OVER, LAG/LEAD), subqueries, Common Table Expressions (CTEs), ACID transaction boundaries, surrogate vs natural keys, UUIDv4 page fragmentation, and ON CONFLICT upsert mechanics.
  • Tier 3: Advanced PostgreSQL Internals (30 Qs): B-Tree leaf pages, page splits, fillfactor tuning, EXPLAIN (ANALYZE, BUFFERS) query plan interpretation, GIN/GiST/BRIN index architectures, MVCC tuple headers (xmin, xmax, t_ctid), declarative table partitioning, PgBouncer pool modes, and Row-Level Security (RLS).
  • Tier 4: Senior PostgreSQL & Production Engineering (30 Qs): Multi-transaction deadlock graph post-mortems, zero-downtime online schema migrations (expand/contract column rename), replication lag mitigation, table bloat remediation (pg_repack vs VACUUM FULL), checkpoint WAL bursts, disaster Point-In-Time Recovery (PITR), and high-availability Patroni split-brain fencing.

Dual Execution Sandbox & AI Evaluation Architecture

In-Browser AlaSQL Sandbox vs Real PostgreSQL:
The platform explicitly distinguishes generic SQL practice from engine-specific PostgreSQL practice. Executable SQL queries run client-side inside an in-browser AlaSQL-99 relational engine with schema introspection, query timeout limits, and row-order normalization. For PostgreSQL-specific architecture (e.g. WAL, MVCC, B-Tree splits, deadlock graphs), the candidate submits their query plan or diagnostic strategy to the Gemini AI Database Evaluator (/api/sql/evaluate), which analyzes query optimality, index usage, and production failure risks against an authoritative rubric.
